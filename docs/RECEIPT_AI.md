# Receipt extraction

Set `GEMINI_API_KEY` in the API environment only. `GEMINI_RECEIPT_MODEL` defaults to `gemini-3.5-flash-lite`; it can be changed to an available Gemini model supporting image/PDF inputs and structured JSON output. Restart the API after changing environment variables. Do not add the key to Nuxt runtime config or any public environment variable.

After a receipt is uploaded and stored, the modal shows extraction progress; the editable form and Save button remain hidden until extraction finishes. The UI calls guarded `POST /ocr/receipts` with `{ "fileId": "<saved file UUID>" }`. It requires `petty-cash.ocr.receipt` and an MPAO identity; local development retains the existing permission bypass. Only the owner of a ready file can request extraction. Arbitrary URLs, paths and inline file contents are not accepted.

The API streams the private stored file to Google's resumable Files API without full-file buffering or base64 conversion. It first classifies the actual document as bill, receipt, invoice, other or unknown, then requests structured vendor, date, total in MVR, invoice number, category and exact purchased line-item descriptions. Product sizes and pack notation are retained; unit conversion notes and payment table entries are excluded. Values are validated on the API; invalid/uncertain values are left for manual entry. Purchased items are joined with commas for “What was bought”. AI suggestions do not verify invoices or create expenses automatically.

The UI retains the existing form layout and uses UI-kit messages for extraction status and retry. After extraction, every field is editable and manually edited fields take precedence over retry suggestions. Unrelated documents and uncertain/unreadable files show an explanatory message and open manual entry without prefilling AI values. Saving waits until extraction finishes or fails. Replacing a file clears previous AI suggestions so they cannot be mistaken for data from the new attachment. Results arriving after save, close, a different attachment or a reset are ignored. An upload failure still requires retrying the upload; an AI failure never invalidates an already-saved attachment.

Single extraction has a 45-second deadline; bulk extraction has a 120-second deadline. Missing configuration returns 501; provider, quota, timeout, unreadable or malformed responses fall back to manual entry (503). Permission errors also leave manual entry available. Receipt/expense creation and settlement have no dependency on AI success. The provider response and API key are not returned or logged.

Temporary Google files are deleted after processing, including generation failures; cleanup has its own five-second deadline. If deletion fails or an interrupted upload leaves an unknown provider file, Google Files API expiry removes it after 48 hours. The application's original private attachment remains available independently.

References: [Google Files API](https://ai.google.dev/gemini-api/docs/files), [structured output](https://ai.google.dev/gemini-api/docs/generate-content/structured-output), [available models](https://ai.google.dev/gemini-api/docs/models).

## Bulk Receipts

The request-detail button beside Add receipt opens a UI-kit modal. Select up to 20 images/PDFs (10 MiB per file); Upload & extract streams each file separately, two at a time, then calls extraction once for all successfully uploaded files. The modal shows queued/uploading/extracting/completed statuses and overall progress, then an editable responsive table. Non-receipts and AI failures show manual-entry messages; failed uploads require retry or removal. Rows may be corrected or removed before confirming. Cancelling ignores late results and leaves unattached uploads for 24-hour cleanup.

Confirm & attach sends all reviewed receipts to `POST /requests/:id/expenses` as `{ receipts: [...], expectedVersion }` with a server-issued Idempotency-Key. File ownership/readiness, unique attachments, request permission/state and revision are checked within one transaction. Either all expenses, file associations and audit history commit or none do. Replaying the same key/payload does not attach duplicates. No new permission is needed beyond existing receipt creation and key issuance.

Anyone allowed to add receipts can also remove them until settlement submission. Both operations lock in pending_closure/closed; Finance's existing return-for-correction flow reopens them. Removed receipt evidence remains stored and audited.

Bulk AI uses the existing `POST /ocr/receipts` with `{ fileIds: [...] }` (1–20 unique IDs), returning `{ receipts: [{ fileId, ...fields }] }`. The single `{ fileId }` contract remains supported. Every file is authorized before any is sent to Google. The provider files are streamed individually; one `generateContent` request contains all file references, one shared instruction prompt and a short numeric label per document. The structured response must contain exactly one result per label; server validation maps labels back to file IDs, so reordered results cannot swap attachments. Duplicate/missing/invalid labels or truncated output fail safely to manual entry. No individual AI retry calls run automatically. Temporary provider files are cleaned together, including partially failed uploads. This removes repeated instruction overhead; document content still consumes tokens.
