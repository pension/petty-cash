# Petty Cash

A URL shortener + QR code manager, split into `petty-cash-ui` (Nuxt) and `petty-cash-api` (NestJS), talking directly over HTTP — no gateway/BFF (unlike the payouts/PCS stack, which routes through `siraathu`).

For authentication (bifrost, `@pension/midgard`/`@pension/midgard-nuxt`, org selection, all the setup gotchas), see **`AUTH.md`** — don't duplicate that here. Everything below is domain logic.

`petty-cash-ui`'s Pinia store (`apps/petty-cash-ui/stores/shorturl.ts`) is wired to the real API — no more mock/hardcoded data. State starts empty; every page fetches on `onMounted`. All mutation actions (`addLink`, `updateQRCode`, etc.) are `async` and call `useHttp()` against `${runtimeConfig.public.apiBase}/...`, checking `response.success` before touching local state.

## Where this came from

There's a spec at `ui-lab/pages/shorturl/api-guide.md`, written before `petty-cash-ui`/`petty-cash-api` existed as a standalone split. It's a reasonable starting skeleton but drifted from reality in places (missing fields the UI actively renders, wrong field names, assumes infra this app doesn't have). The schema and endpoints below follow **the current `petty-cash-ui` code as ground truth** wherever the two disagreed — don't "fix" this backend to match the guide without re-checking against the actual frontend first.

## Data model (`apps/petty-cash-api/prisma/schema.prisma`)

MySQL (not Postgres like the original guide — matches this org's actual convention; local dev connects to `mysql://root:root@localhost:3306/petty-cash`, same root/root credentials as `payouts-api`/`pcs-api`'s local setup).

**Naming**: Prisma model/field names stay camelCase (`ShortLink.longUrl`, etc. — that's what the generated TS client and every service/DTO use), but every table and column is `@@map()`/`@map()`'d to snake_case in the actual DB (`short_link.long_url`). If you add a new model or field, map it — don't let a bare camelCase column slip into the schema. `FrameType`'s enum values were already `@map()`'d to hyphenated wire strings before this convention existed (see the gotcha below); that's unrelated and unaffected.

- **`ShortLink`** — `title`, `longUrl`, `shortCode` (unique), `shortUrl`, `clicks`, `tags` (`Json`, not a native array — MySQL/Prisma doesn't support `String[]`; store an array of strings and cast in TS), `expiresAt`, `status` (`active`/`archived`; a link is displayed as "expired" purely by comparing `expiresAt` to now, there's no separate DB status for it).
  - `LinkHistoryEvent` (`label`, `description`, `by`, `createdAt`) — an edit audit trail, one row per create/meaningful-update. Rendered by `links/[id].vue` via `PoLogs`. This is real, actively-used UI, not speculative — don't remove it thinking it's unused.
  - `LinkDestinationHistory` (`destinationUrl`, `changedBy`, `isCurrent`, `effectiveFrom`) — every distinct `longUrl` a link has pointed to, only the newest `isCurrent: true`. Also rendered on `links/[id].vue`.
  - `by`/`changedBy` are the actor's bifrost display name (`@BifrostUser()`'s `user.name`), not a foreign key — `petty-cash-api` doesn't own a Users table, bifrost does.
- **`QRCode`** — `title`, `longUrl`, `scans`, `color`, `bgColor`, `style`, `corner`, `overlayType`, `overlayText`, `logo`, plus `templateId`/`frameId` (optional relations) and `linkId` (optional but `@unique` — every link gets exactly one auto-generated QR code; see "QR generation is tied to link creation" below). `onDelete: Cascade` on `linkId` — deleting a link deletes its QR (and that QR's own `EngagementEvent` rows, which already cascade from `QRCode`).
- **`QRTemplate`** / **`QRFrame`** — reusable design presets, managed from `settings/index.vue`. `QRFrame.frameType` uses the `FrameType` enum.
- **`EngagementEvent`** — one row per click/scan, written by the redirect engine (see below).
- No `Campaign` model. The frontend store has full campaign CRUD scaffolding (`campaigns[]`, `campaignId` on links, `addCampaign`/etc.) but zero UI actually exposes it — deliberately left out until a real UI entry point exists. Don't add it speculatively.

**Field naming**: the API uses `clicks`/`scans`, not `clicksCount`/`scansCount` like the original guide — this matches what `stores/shorturl.ts`'s `LinkItem`/`QRCodeItem` and every page already expect, so wiring the real frontend up later needs no field renaming.

**`FrameType` wire format gotcha**: `petty-cash-ui` sends/expects hyphenated strings (`'bottom-label'`, `'top-header'`, `'border'`, `'card-box'`, `'custom-upload'` — see `settings/index.vue`'s `frameTypeOptions`), but Prisma's generated client only accepts/returns the underscored enum member names (`bottom_label`, etc. — the hyphenated forms are just `@map()`'d DB values, invisible to the TS client). `src/common/frame-type.util.ts` has the bidirectional translation (`FRAME_TYPE_WIRE_TO_PRISMA` / `FRAME_TYPE_PRISMA_TO_WIRE`) — every service that touches `frameType`/`qrFrame` needs to go through it. If you add a new endpoint that returns a bare Prisma `QRFrame`/`QRTemplate` without running it through `toWire()`, the frontend will get an enum value it's never seen and won't match against its own option list.

## API (`/api/v1/shorturl/*`, all guarded with `IdentityGuard` — see `AUTH.md`)

- `LinksModule` — full CRUD at `/links`. `PATCH /links/:id` deliberately has no `customBackHalf` field in its DTO — both edit forms in `petty-cash-ui` disable that field after creation, so the backend never accepts changing it either. `POST /links` also accepts an optional `templateId` and auto-creates the link's `QRCode` in the same call — see "QR generation is tied to link creation" below.
- `QrCodesModule` — full CRUD at `/qrcodes`, still used directly by `links/[id].vue`'s customizer (`PATCH /qrcodes/:id` to save design changes) and the render/download endpoint. No bulk endpoints, and no standalone create flow in the UI anymore (see below) — `POST /qrcodes` (`QrCodesController.create`) still exists at the API level but nothing in `petty-cash-ui` calls it; `LinksService.create()` does its own nested `qrCode: { create: {...} }` Prisma write rather than calling into `QrCodesService`.
- `TemplatesModule` / `FramesModule` — full CRUD at `/templates` / `/frames`, matching `settings/index.vue`'s save handlers field-for-field. `customImageUrl` on frames is a base64 data URI from the browser's `FileReader` — no separate file storage.
- `AnalyticsModule` — `GET /analytics/global`, `GET /analytics/links/:id`, `GET /analytics/qrcodes/:id`, `?range=7d|30d|all`. Returns `dates`/`clicks`/`scans`/`engagements`/`totalEngagements`/`countries`/`cities`/`devices`/`referrers`, matching what `analytics/index.vue` and `analytics/[id].vue` already consume. Aggregation is done **in application code** (fetch matching `EngagementEvent` rows, bucket/tally in JS), not SQL-level `GROUP BY` — fine at current scale, revisit if the events table gets large. The frontend's 7d/30d/all range selector is wired (`analytics/index.vue`'s `rangeMap` translates the UI labels to `7d`/`30d`/`all`).
- `QrCodesModule` also has `POST /qrcodes/render?format=svg|png` — see "QR rendering" below.

**CORS**: `petty-cash-api`'s `main.ts` calls `app.enableCors()` (no origin restriction), matching `pcs-api`'s convention for a direct-HTTP-consumed backend. Needed because `petty-cash-ui` and `petty-cash-api` run on different ports/origins in dev with no gateway in front.

## Redirect engine (public — no `/api/v1` prefix, no `IdentityGuard`)

`GET /:code` (click) and `GET /r/:code` (scan) in `RedirectModule`. Looks up `ShortLink` by `shortCode`; `410 Gone` if expired or archived; otherwise parses the request's User-Agent synchronously (`ua-parser-js`), writes an `EngagementEvent`, increments `ShortLink.clicks`, and `302`s to `longUrl`. `/r/:code` additionally looks up the `ShortLink`'s own `QRCode` (via `linkId`, now a 1:1) and credits the scan to it too (increments `QRCode.scans`, sets `qrCodeId` on the event) — this is the *only* path that credits scans, which is why every generated QR image encodes `https://<SHORT_DOMAIN>/r/<shortCode>` and not the raw destination `longUrl` (see below) — encoding `longUrl` directly would mean scanning the QR never touches this backend at all.

**No async queue.** The original guide's design pushes click/scan events to a Redis/BullMQ queue for async UA parsing. This implementation does that work synchronously inside the request instead — deliberate simplification, not an oversight. Revisit if redirect latency becomes a real problem.

**GeoIP** (`src/common/geoip.util.ts`'s `lookupGeo()`) uses `geoip-lite` — a bundled, in-process MaxMind GeoLite2-style DB, synchronous lookup, no network call, no API key. Chosen over an external geolocation API (the pattern from an earlier version of this app) specifically because this traffic volume doesn't need one: an external call would add per-redirect latency and a network dependency for no real benefit at this scale; `geoip-lite`'s only real cost is that its bundled data file goes stale between package updates, which is fine for internal marketing-traffic analytics. `RedirectController.resolve()` calls it alongside the existing UA parsing and writes `countryCode`/`countryName`/`cityName` onto the `EngagementEvent` it creates — country name is derived from `geoip-lite`'s ISO alpha-2 code via `Intl.DisplayNames` (no extra dependency needed for that translation). **Only resolves for real public IPs** — loopback/private ranges (`127.0.0.1`, `::1`, `10.x`, etc.) always return nulls by design, so this can't be meaningfully exercised against `localhost` traffic in local dev; `AnalyticsService`'s `tally()` fallback (`'Unknown'`) is what you'll still see there, correctly.

**Client IP resolution** (`src/common/client-ip.util.ts`'s `getClientIp()`) — deliberately not just `req.ip`/`req.socket.remoteAddress`, since behind Cloudflare (or any reverse proxy) that's the proxy's own address, not the visitor's, which would make GeoIP resolve every event to the same wrong location. Priority: `cf-connecting-ip` header (set directly by Cloudflare's edge — trustworthy as long as this app is only reachable *through* Cloudflare, not also directly) → `x-forwarded-for` (first hop only — best-effort if there's a proxy but it isn't Cloudflare) → the raw socket address (direct connections, e.g. local dev with no proxy in front at all). No Express `trust proxy` setting is used for this — Express's built-in mechanism only understands `X-Forwarded-*`, not Cloudflare's own header, so it wouldn't help here anyway.

**Route ordering matters.** `RedirectModule` is imported *last* in `AppModule` specifically so its `GET /:code` wildcard can't shadow literal routes registered by every other module (or `AppController`'s `/whoami`). Verified directly: hitting `/whoami`, `/api/v1/midgard/permissions/sync`, and every `/api/v1/shorturl/*` route all resolve correctly, not swallowed by the wildcard. If you add a new top-level (non-`/api/v1`) route, add its module *before* `RedirectModule` in `AppModule`'s imports, or it'll get shadowed.

**Local `SHORT_DOMAIN`**: locally it's `localhost:4000` (petty-cash-api's own port, where this redirect engine actually lives), not `localhost:3000` (petty-cash-ui's port) or `mpo.mv` (the production domain). `petty-cash-ui` is a pure SPA with no route that could catch arbitrary short codes without colliding with its own pages (`/links`, `/qrcodes`, etc.), so pointing `SHORT_DOMAIN` at port 3000 would make every generated link 404 instead of redirecting/tracking. `SHORT_DOMAIN` is baked into `ShortLink.shortUrl` at creation time (`links.service.ts`, and `prisma/seed.ts` for the demo link) — changing the env var doesn't retroactively update already-created rows.

This value exists as an env var in **both** apps and they must be kept in sync: `apps/petty-cash-api/.env`'s `SHORT_DOMAIN` (what actually gets baked into `shortUrl`) and `apps/petty-cash-ui/.env`'s `NUXT_PUBLIC_SHORT_DOMAIN` (`runtimeConfig.public.shortDomain` — not currently read anywhere in `petty-cash-ui`'s own code, but kept matching so it's correct if/when something does use it, e.g. a "yourdomain.com/____" preview in the create-link form).

## QR rendering (`@petty-cash/qr-render` + render/download endpoint)

`packages/qr-render` is a shared yarn workspace package (plain TS, its own `tsc` build to `dist/`) exporting pure functions — `buildQrMatrix`, `getPatternModules`, `getCornerEyes`, `buildQrSvg(params)` — ported from what used to be `qrcodes/[id].vue`'s inline template (the canonical, full 9-pattern/9-corner implementation; `QRCodePreview.vue` had drifted to a smaller subset with generic fallbacks). Both `petty-cash-ui` and `petty-cash-api` depend on it (`"@petty-cash/qr-render": "0.0.1"`, hand-added to `package.json` since yarn v1 can't `add` a workspace-local fake-scope package — re-add by hand + `yarn install` if it's ever dropped).

- **`petty-cash-ui`**: `components/QRCodePreview.vue` and `pages/links/[id].vue`'s customizer both call `buildQrSvg(...)` and render the result via `v-html` instead of maintaining their own template logic — this fixed a pre-existing style/corner inconsistency between the two as a side effect. `nuxt.config.ts` needs `vite.resolve.preserveSymlinks: true` for this to build in production — without it, Rollup's CJS-interop heuristics fail on the symlinked workspace package (resolves outside `node_modules` to its real path, so the usual named-export detection doesn't apply). An earlier attempt with `optimizeDeps.include` did not fix this; only `preserveSymlinks` did.
- **`petty-cash-api`**: `QrCodesService.render(dto, format)` calls `buildQrSvg` directly, then for `format=png` rasterizes with `sharp` (`sharp(Buffer.from(svg)).resize(1024, 1024).png().toBuffer()` — the `.resize()` is required: the SVG's `viewBox` is in tiny QR-module units, ~25-45, so a bare `sharp(svg).png()` defaults to a near-unusable ~30px image). Needs `esModuleInterop: true` in `tsconfig.json` (was missing — `allowSyntheticDefaultImports` alone only suppresses the TS *type* error for `sharp`'s default import, not the actual broken interop code emitted at runtime).
- **Download endpoint**: `POST /api/v1/shorturl/qrcodes/render?format=svg|png`, guarded like the rest of `QrCodesModule`. **Stateless by design** — the request body is whatever design is currently on screen (`fgColor`/`bgColor`/`style`/`corner`/`overlayType`/`overlayText`/`value`), not a DB lookup by QR code ID. This means the download button doesn't require hitting Save first. Frame compositing (borders/labels/custom-upload background) is now supported too — see "Frame is a real, independent step" below for `buildFramedQrSvg` and the PNG compositing workaround for custom-upload backgrounds.
- `pages/links/[id].vue`'s `downloadQR(format)` calls this endpoint via `useHttp(..., { download: true })`, which handles the blob-download mechanic — see below for what `value` it sends and why.

## QR generation is tied to link creation — there is no standalone QR flow

There used to be an independent QR-code flow (`/qrcodes` list, `/qrcodes/create`, `/qrcodes/[id]` customizer) that let a `QRCode` exist with no `ShortLink` at all. That's gone. The reasoning: the redirect engine's scan-crediting (`GET /r/:code`, see above) only works through a `ShortLink`'s `shortCode` — a standalone QR's `longUrl` was encoded directly into the image with zero backend involvement, so scanning it never got tracked no matter what. Since QR *stats* only exist through the URL shortener, QR creation now only exists through it too.

- **Every `ShortLink` gets exactly one auto-generated `QRCode`** at creation time. `QRCode.linkId` is `@unique` (see the schema note above) and `onDelete: Cascade` — deleting a link deletes its QR. Links created before this change (if any survive in a given DB) have no `QRCode` row; `links/[id].vue` renders a fallback "no QR code yet" state for those rather than assuming one always exists.
- **`POST /links` accepts an optional `templateId`.** `LinksService.create()` looks the `QRTemplate` up (a stale/deleted ID silently falls through rather than failing link creation) and copies its `fgColor→color`/`bgColor`/`style`/`corner`/`overlayType`/`overlayText`/`frameId` onto the new QR's nested `create`. Fields left `undefined` when there's no template let `QRCode`'s own Prisma column `@default`s apply exactly — no separate "defaults" object needed. `links/create.vue` has a template-picker section (real `store.templates`, fetched via `store.fetchTemplates()` in `onMounted` — not a hardcoded list) wired to this.
- **The QR image always encodes the link's `/r/:code` scan URL, never `longUrl` or the plain `shortUrl`.** `links/[id].vue` builds it as `` `https://${config.public.shortDomain}/r/${link.value.shortCode}` `` (this is why `LinkItem`/`mapLink()` now expose `shortCode`, not just `shortUrl` — it didn't before). Getting this value right is the entire point of tying QR generation to links; encoding anything else silently defeats scan tracking the same way the old standalone flow did. Both the live preview (`qrSvg`) and the download call (`downloadQR`'s request body) use this same `qrValue`.
- **QR design/download lives inside `links/[id].vue`**, not a separate route — a compact summary card (preview + download buttons) plus a full "Customize QR Code" section below the main grid (templates, pattern/corner pickers, colors, overlay, frame, live preview — ported from the old `qrcodes/[id].vue`, which no longer exists). `saveDesignSettings()` there sends the full field set (`color`/`bgColor`/`style`/`corner`/`overlayType`/`overlayText`) — this fixes a previously-documented bug where the old page's save handler silently dropped `overlayType`/`overlayText`. It deliberately does **not** send `frameId`/`qrFrame` — the local "Select frame" control (`frameOptions`, carried over verbatim) only ever held 3 fake local labels (`none`/`border`/`bottom-label`), never real `QRFrame.id` values from `store.frames`, so there's nothing real to persist there; sending it would write garbage into a real FK. That's a pre-existing gap (the frame picker was never wired to real `QRFrame` presets, even in the old page), not something this change fixes — don't assume `frameId` round-trips through this form.
- **No static thumbnail images exist in this app** (`public/images/` doesn't exist at all — zero PNGs anywhere in `petty-cash-ui`). The old `qrcodes/[id].vue`'s pattern/corner pickers referenced `/images/<id>.png` paths that were never real, always rendering broken-image icons — carried over into `links/[id].vue` at first for the same reason, then fixed: `patternPreviewSvg()`/`cornerPreviewSvg()` render an actual tiny `buildQrSvg(...)` preview per option instead (same approach as `templatePreviewSvg()` for the template picker). If you add another design-option picker anywhere, don't reach for a `/images/...` path — nothing will be there.
- **Store cleanup**: `addQRCode`/`deleteQRCode` were removed from `stores/shorturl.ts` (their only callers were the deleted pages). `fetchQRCodes`/`fetchQRCode`/`getQRCodeById`/`updateQRCode` are kept — `fetchQRCodes` because `getTotalScans`/`getTotalEngagements` (used by the dashboard and `/analytics`) reduce over `state.qrcodes`, which only that action populates; both `pages/index.vue` and `pages/analytics/index.vue` now call it in `onMounted` for exactly that reason. `fetchQRCode`/`getQRCodeById` are kept because `pages/analytics/[id].vue` (a separate, already-unreachable page — nothing links to `/analytics/:id`, confirmed via repo-wide search) still references them; that page is out of scope for this change, left as-is.
- Settings' "Use in QR" button on a template card now routes to `` `/links/create?templateId=${tmpl.id}` `` (previously went to the now-deleted `/qrcodes/create` and didn't even pass which template). `links/create.vue` reads `route.query.templateId` on mount to pre-select it in the picker.

## `useHttp()`'s `method` option must be UPPERCASE — `'patch'` silently breaks CORS

`stores/shorturl.ts` (and one direct call in `qrcodes/[id].vue`'s `downloadQR`) originally passed lowercase method strings (`'get'`, `'post'`, `'patch'`, `'delete'`) to `useHttp()`. `@pension/midgard-nuxt`'s `useHttp()` passes that string straight to native `fetch()` with no normalization. The Fetch spec only auto-uppercases `GET`/`HEAD`/`POST`/`PUT`/`DELETE`/`OPTIONS` for you — **`PATCH` is explicitly excluded from that list** — so `fetch(url, { method: 'patch' })` sends the literal lowercase string on the wire. The `cors` npm package's preflight response always reflects its configured methods in uppercase (`Access-Control-Allow-Methods: GET,HEAD,PUT,PATCH,POST,DELETE`), and the CORS spec requires a byte-for-byte case-sensitive match — so a lowercase `patch` request gets rejected by the browser at the preflight stage with `Method patch is not allowed by Access-Control-Allow-Methods in preflight response`, even though the exact same request succeeds fine via `curl` (curl doesn't enforce CORS at all) or against the server directly.

This broke **every** update/edit action in the app (`updateLink`, `updateQRCode`, `updateTemplate`, `updateFrame`, `saveDesignSettings`, etc. — anything using PATCH) while leaving fetches/creates/deletes (GET/POST/DELETE, which *do* get auto-uppercased) looking completely fine — which is why it read as "everything works except editing," not as an obvious blanket outage. Fixed by uppercasing every method string in `stores/shorturl.ts` and the one other direct `useHttp()` call site. If you add a new `useHttp()` call anywhere, use uppercase methods — don't rely on the Fetch spec's partial auto-normalization to save you, since it silently doesn't cover PATCH.

**Diagnostic note for next time**: `useHttp()`'s catch block only knows how to unpack `ofetch`'s `FetchError` type, but it uses native `fetch()`, which throws a plain `TypeError` instead. So a *real* CORS/network-level failure gets silently swallowed into `{ error: null, success: false }`, and store actions that do `throw new Error(response.error?.message || 'Failed to X')` end up throwing the generic fallback message with zero diagnostic info — the browser console's terse `net::ERR_FAILED` plus a separate `Access to fetch at ... has been blocked by CORS policy: <reason>` line (or the Network tab's Headers view) is the only place the real reason shows up. This is a bug in `@pension/midgard-nuxt` itself, not something to fix in this repo.

## Don't swallow the real error message in a bare `catch {}`

Store actions like `addLink`/`addQRCode`/etc. `throw new Error(response.error?.message || 'Failed to X')` — that real backend message (e.g. `"Short code \"ABC123\" is already in use."`) is genuinely useful and specific. `pages/index.vue`'s dashboard quick-shorten box and `pages/links/create.vue` both used to catch with a bare `catch { ... }` and show a hardcoded generic string instead (`'Something went wrong shortening this link'`), discarding the real reason — and the dashboard one didn't even call `showToast()`, only set inline text under the input, so a background failure was easy to miss entirely. Fixed by catching the error (`catch (err)`) and using `err.message` when it's an `Error` instance, falling back to the generic string only for non-`Error` throws. If you add a new create/update handler that calls a store action, do the same — don't default to a canned message when the thrown error already has a specific one. (The other bare `catch {}` blocks in the app are fine as-is: client-side URL-format validation has no backend message to surface, and `downloadQR`'s catch wraps a raw `useHttp()` call that doesn't throw structured errors in the first place.)

## Zod DTOs must match what petty-cash-ui actually sends, not what "should" be required

The Zod schemas were originally written from the model/API-guide shape rather than cross-checked against `petty-cash-ui`'s actual submit handlers, and drifted in ways that made real requests fail even though the payload was exactly what the UI legitimately sends:

- **`title`** on `CreateLinkSchema`/`CreateQRCodeSchema` had `.min(1)`, but neither `links/create.vue` nor `qrcodes/create.vue` validates Title before submit (only the URL field is required client-side) — an empty title 400'd with no indication why. Fixed by dropping `.min(1)` (kept `.max(120)`); the DB column has no NOT-EMPTY constraint either, just NOT NULL, so an empty string is a fine value.
- **`expiresAt`** used `z.string().datetime()`, which only accepts a full ISO-8601 instant (`...T...Z`). `links/create.vue`'s expiration picker is `<input type="date">`, which produces a bare `YYYY-MM-DD` — this rejected on *every* link creation with expiration enabled, not just an edge case. Fixed via `src/common/zod.util.ts`'s `dateStringSchema` (a permissive `Date.parse()` refinement instead of the strict format), used by both `create-link.dto.ts` and `update-link.dto.ts`.
- **`qrFrame`** on `CreateTemplateSchema` reused `FRAME_TYPE_WIRE_VALUES` (the same enum as `QRFrame.frameType`), which has no `'none'` member — but `settings/index.vue`'s `handleSaveTemplate` always sends `qrFrame: 'none'` when no `QRFrame` preset is selected (`chosenFrame ? chosenFrame.frameType : 'none'`), since a template's "no frame" state is a real, common case. Fixed with a dedicated `QR_TEMPLATE_FRAME_VALUES` constant (`'none'` plus the real frame types) in `frame-type.util.ts` — don't just add `'none'` to `FRAME_TYPE_WIRE_VALUES` itself, since that list is also `QRFrame.frameType`'s own enum, where "no frame" isn't a valid concept for a frame record.

When adding or touching a DTO, check the *actual* submit handler in `petty-cash-ui` for that form (what it validates before calling the store, and exactly what object literal it passes) — don't assume a field is required just because the underlying DB column is `NOT NULL` or the "obvious" design would require it.

## `PoSelectField` needs the `object` prop whenever `v-model` holds an object

`@pension/ui-kit`'s `PoSelectField` takes a `:list` of `{id, name, ...}` items, but by default matches/returns just the `id` (a primitive) — it only accepts and returns the full item object if the boolean `object` prop is explicitly set. Every metric-switcher dropdown ("Performance Over Time" on `links/[id].vue`, `analytics/index.vue`, `analytics/[id].vue`) and both link-status dropdowns (`links/index.vue`, `links/[id].vue`'s edit modal) initialize their `v-model` ref with a full option object (e.g. `selectedMetric = ref(metricOptions[0])`, `statusSelected: { id: 'active', name: 'Active' }`) but were missing the `object` prop — so the component could never reconcile that object against its list to know what's selected, and rendered as empty by default despite the underlying ref genuinely holding the first option's data. Fixed by adding `object` to all five. If you add a new `PoSelectField` anywhere and bind `v-model` to something other than a bare id/string, add `object` too — the empty-by-default symptom is easy to misread as "the ref never got initialized" when it's actually a component-matching issue.

## Security notes

- **`@petty-cash/qr-render`'s `buildQrSvg()` escapes `fgColor`/`bgColor`/`overlayText` before interpolating them into SVG** (`escapeSvg()` at the top of the file). This was a real, fixed stored-XSS: `overlayText` lands as literal SVG element *text content*, not just an attribute, and none of these three fields ever had format/length validation anywhere upstream (Zod DTOs or DB columns) that would have prevented a breakout payload. Since the resulting SVG is rendered via `v-html` in several places — including `links/create.vue`'s template picker, which renders a live preview of *every* saved `QRTemplate` with no user action required — a malicious `overlayText` saved to a shared `QRTemplate` would have fired for every user who simply visited `/links/create`. Combined with `@pension/midgard-nuxt` storing bearer/refresh tokens in `localStorage` (not httpOnly cookies), that's a direct path to session theft, not just a cosmetic injection. If you ever add a new field to `BuildQrSvgParams` that gets interpolated into the SVG string, escape it the same way — don't assume upstream validation is enough, since the renderer is the one place guaranteed to see every code path (including the stateless render endpoint, which has no DB column backing its inputs at all).
- **`cssColorSchema`/`httpUrlSchema`** (`src/common/zod.util.ts`) — defense-in-depth on top of the escaping fix above: `color`/`bgColor`/`fgColor` fields across `create-qrcode.dto.ts`, `render-qrcode.dto.ts`, and `create-template.dto.ts` now reject anything that isn't a plausible hex color or CSS color name at the API boundary; `longUrl` across `create-link.dto.ts`/`update-link.dto.ts`/`create-qrcode.dto.ts` now rejects any scheme other than `http`/`https` (plain `z.string().url()` accepts `javascript:`/`data:`/anything the WHATWG `URL` parser accepts — modern browsers generally won't act on those from a redirect `Location` header, but there was no explicit restriction anywhere).
- **No per-user ownership / IDOR by design** — any authenticated user (any valid bifrost token) can read, edit, or delete *any* link, QR code, template, or frame. `actor`/`by`/`changedBy` on history records are audit-log display strings only, never used for access control. This may be intentional for a small shared internal tool, but it means one compromised token exposes and can modify everyone's data — worth a deliberate decision if this ever needs tightening, not an oversight to silently "fix."
- **No rate limiting anywhere** — not on the redirect engine (click/scan spam could inflate stats or waste GeoIP lookups) or on any guarded endpoint. Low urgency at current traffic; revisit if that changes.
- **CORS is a bare wildcard** (`app.enableCors()`, no origin restriction — see the CORS note above). Lower risk than it would be for a cookie-authenticated app, since bearer tokens aren't automatically attached to cross-origin requests the way cookies are, but still looser than necessary for a production deployment.

## Frame is a real, independent step — decoupled from Template

Template controls the QR's own pixel-level look (pattern/corner/colors/overlay); Frame is a separate, optional "wrap it in this" decision applied afterward, not baked into a saved Template. This wasn't always true — `QRTemplate` used to carry `frameId`/`qrFrame`/`qrFrameText`, letting a template drag a frame along with it — those three columns are gone now.

- **Frame selection lives in `links/create.vue`** (a "QR Code Frame" step after the theme picker) **and `links/[id].vue`'s customizer** (an "Apply a frame" section), both pulling from the real `store.frames`/`GET /frames` library — not a fake local list. Selecting persists to `QRCode.frameId` (which already existed on the model — it just had nothing writing to it before this).
- **Picker cards, the sidebar summary, and the live preview all render via `buildFramedQrSvg` + `v-html`, not the `<QRFramePreview>` DOM/CSS component.** `QRFramePreview.vue`'s inner `QRCodePreview` uses a fixed pixel size per `size="sm"|"md"|"lg"` (e.g. `140px` for `sm`) that doesn't scale down to fit a smaller parent — giving it a small `width`/`height` only shrinks the outer box, so the QR gets clipped by `overflow-hidden` instead of scaling, rendering as a "zoomed in"/cropped preview (reported with a screenshot: a picker card showing only a corner of the frame). `buildFramedQrSvg`'s output is `viewBox`-based SVG, so it scales cleanly to any container size — same fix already applied to the template picker (`templatePreviewSvg`). If you add another frame preview anywhere, use `buildFramedQrSvg` + `v-html`, not `<QRFramePreview>`, unless it's genuinely rendered at its native `220x270` size.
- **`POST /links` takes `frameId` as its own sibling field to `templateId`** (`create-link.dto.ts`), not derived from the template — `LinksService.create()` sets it straight from `dto.frameId`. Settings' Template editor no longer has any frame-picker UI at all; the standalone "QR Code Frames" tab (create/edit/delete real `QRFrame` presets) is the only place frames get authored, same as before.
- **`saveDesignSettings()` in `links/[id].vue` now actually sends `frameId`** — this was the specific gap called out in an earlier version of this doc ("nothing real to persist"). Now there is.

### Frame-aware rendering and download (`buildFramedQrSvg`)

`packages/qr-render` exports `buildFramedQrSvg(params)` alongside `buildQrSvg` — a from-scratch SVG port of `QRFramePreview.vue`'s CSS layout (fixed `220x270` box, colored banner or plain-box background depending on `frameType`, QR sized/positioned within the remaining body area via `qrPosition`/`qrSizePercent`). It embeds the QR itself via a **nested `<svg>` element** rather than reimplementing QR rendering, so `buildQrSvg` stays the single source of truth for the QR — only the frame chrome is new code. Same escaping discipline as `buildQrSvg` applies to every interpolated field (`frameColor`/`textColor`/`borderColor`/`ctaText`/`customImageUrl`) — this is a faithful, not pixel-perfect, port; SVG text/layout doesn't need to match a browser's CSS box model exactly for a downloadable image.

**A real, confirmed constraint drove the design here, not a guess**: `sharp` (what `QrCodesService.render()` uses for PNG downloads) **cannot rasterize an embedded data-URI `<image>` element** — confirmed directly by testing a minimal, isolated SVG with nothing else in it; it fails silently (an all-white/blank result), unlike any real browser or SVG viewer, which render embedded images fine. This only matters for `frameType: 'custom-upload'` (the only case with a background image). The fix: `buildFramedQrSvg` takes a `transparentBackground` option that skips the box fill and the `<image>` entirely; `QrCodesService`'s PNG path for `custom-upload` composites two *separate raster layers* via `sharp`'s own `.composite()` — the background photo resized on its own, and a `transparentBackground: true` chrome-only render (border + QR + banner/caption) layered on top — rather than relying on SVG-embedded image rendering at all. SVG-format downloads and the live browser preview don't have this problem (real SVG consumers support embedded images) and use the normal, full `buildFramedQrSvg` output with the image embedded directly.

`QrCodesService.render()`'s PNG/SVG sizing also had to stop assuming square: the bare QR's `1024x1024` constants only apply to `renderBare()`; `renderFramed()` derives width/height from the frame box's actual `220:270` ratio (`FRAME_BOX_WIDTH`/`FRAME_BOX_HEIGHT`, exported from `@petty-cash/qr-render` specifically so the backend doesn't hardcode the same numbers twice).

`render-qrcode.dto.ts`'s `RenderQRCodeSchema` gained an optional `frame` object mirroring `QRFrame`'s renderable fields, passed inline (not by ID) — matches this endpoint's existing stateless "render exactly what's on screen" design, same as `fgColor`/`style` already being inline rather than looked up.

## `petty-cash-api` didn't exit cleanly on Ctrl+C

`main.ts` had zero `SIGINT`/`SIGTERM` handlers at all — unlike `payouts-api`/`pcs-api`, which both explicitly listen for both signals and call `app.close()`. Two real, confirmed contributing factors, not just a guess:
1. Without any signal handler, shutdown depended entirely on Node's default disposition reaching the process — which some process trees don't reliably forward through. `nest start --watch` in particular runs the actual app as a child of a webpack-watch parent, and this session repeatedly needed manual `kill <pid>` on a lingering child/parent after Ctrl+C during development (see the earlier "never manage dev servers" feedback note — this is exactly the failure mode that caused it).
2. Even when the signal *does* reach the process, `@pension/midgard`'s `IdentityService` opens its own `ioredis` connection directly in its constructor with **no cleanup hook anywhere** (confirmed by reading the installed package — no `OnModuleDestroy`/equivalent exists on it at all). That keeps a persistent TCP connection and reconnect timers alive, which alone can stop a Node process from exiting even after `app.close()` resolves.

Fixed by adding explicit `SIGINT`/`SIGTERM` handlers that call `app.close()` (best effort) and then unconditionally `process.exit(0)` regardless of what's still open — this guarantees a clean exit even with the un-closable Redis handle. It does **not** fix a scenario where the signal never reaches the process at all (a `nest start --watch` process-tree quirk, not something fixable from inside `main.ts`) — if Ctrl+C still leaves something running after this, the next thing to check is whether the signal is reaching the child process in the first place, not this file.

## `ClicksChart.vue` needs an unmount guard — race with its own async chart-init

`components/ClicksChart.vue` (used on both the dashboard and `links/[id].vue` — navigating between the two unmounts one instance and mounts another) builds its chart via `initChart()`, which is `async` and does `await loadApexCharts()` (`composables/useApexCharts.ts`, a dynamic `import('apexcharts')`) before touching `chartContainer.value`/creating the `ApexCharts` instance. Nothing guarded that gap against the component having already unmounted by the time the `await` resolves — navigating from a link detail page back to the dashboard quickly enough (both pages render a `ClicksChart`) could resume `initChart()` after `onBeforeUnmount` had already run, either touching a DOM node Vue had already torn down or creating an `ApexCharts` instance that then never gets `destroy()`'d. Symptom: `[Vue warn]: Unhandled error during execution of component update` / `Uncaught (in promise) TypeError: Cannot destructure property 'type' of vnode as it is null`, with the URL updating but the new page's content never actually rendering. Fixed with an `isUnmounted` flag set in `onBeforeUnmount` and checked right after the `await` inside `initChart()`, plus nulling `chartInstance` after `destroy()` so a stale reference can't be reused. Unrelated to the QR/Frame work above — a pre-existing race that fast navigation between the two chart-bearing pages was always capable of triggering.

## Staging deploy (`Dockerfile.api`, `Dockerfile.ui`, `cloudbuild-stag-api.yml`, `cloudbuild-stag-ui.yml`, `iac/staging/`)

Pattern copied from `payouts-api`/`payouts-ui` (Cloud Build v2 GitHub connection + push trigger via Terraform; the Cloud Run service itself is deployed imperatively by `gcloud run deploy` inside each `cloudbuild-stag*.yml`, not by Terraform — `iac/staging/outputs.tf` only exposes the connection/repo/trigger ids, matching payouts-api's own outputs).

**Two separate Dockerfiles** (`Dockerfile.api`, `Dockerfile.ui`), not one shared file with `--target`. That was the original design — a single `Dockerfile` with `api-runner`/`ui-runner` final stages selected via `docker build --target` — and it's a reasonable pattern in general, but **this specific Cloud Build environment doesn't prune un-targeted stages the way BuildKit does**: the classic builder builds *every* stage in a Dockerfile top to bottom regardless of `--target`, only stopping once it reaches the named one. Confirmed directly from a real build log: a `--target=ui-runner` build was observed also building `api-development`, `ui-development`, and `api-runner` — stages with zero relationship to the UI. Since `api-runner` sat earlier in the file, building the UI target unavoidably built the API's runner stage too, which needed `apps/petty-cash-api/.env` — a file only `cloudbuild-stag-api.yml`'s own `SetupEnv` ever creates. Both pipelines were quietly building *both* apps' full builder stages (`nest build` **and** `nuxt build`, every single push, regardless of which one actually changed) — the `--target` flag was only ever picking which stage got *tagged*, not which stages actually ran. Splitting into two files fixes both the correctness bug and the wasted build time in one move — each pipeline now only ever touches its own app.

This is still a yarn v1 workspaces monorepo (`apps/petty-cash-api`, `apps/petty-cash-ui`, `packages/qr-render`), and yarn v1 has no per-workspace install (`yarn workspaces focus` is yarn 2+), so *each* file's `deps` stage still needs every workspace's `package.json` present to resolve against the single root `yarn.lock` — that part of the duplication between the two files is unavoidable, just much cheaper than duplicating the actual build step. Real things that came out of this being a monorepo, true for both files:

- **Docker build context is the repo root**, not `apps/petty-cash-api` or `apps/petty-cash-ui`, for the same reason above.
- **`apps/petty-cash-ui`'s `postinstall` script has to be copied into `Dockerfile.api`'s `deps` stage too**, even though that image never builds `petty-cash-ui`. It declares `"postinstall": "node scripts/copy-ui-kit-css.js"`, and yarn v1 runs *every* workspace's postinstall hook on a root `yarn install`, regardless of which app you're actually about to build — the script file has to already exist on disk for that hook to succeed, not just the `package.json` that references it. Caught by re-deriving the dependency graph by hand (checking every workspace's `package.json` for `postinstall`/`prepare` scripts) before it ever caused a real failure.
- **`node_modules/@petty-cash/qr-render` is a yarn-workspaces symlink** (`node_modules/@petty-cash/qr-render -> ../../packages/qr-render`, confirmed against the real local install) — copying `node_modules` into either file's `runner` stage carries that symlink over as-is, so `packages/qr-render/{package.json,dist}` has to exist at that same relative path in the final image too, or the symlink dangles. Both files copy them there explicitly rather than trying to flatten `qr-render`'s `dist` into `node_modules/@petty-cash/qr-render/dist` directly (tried first, then reasoned through why it would leave a broken symlink and switched before it ever got built).
- `Dockerfile.api`'s `deps` stage still installs `apps/petty-cash-ui`'s deps (the whole Nuxt/Vite/ui-kit toolchain) — an unavoidable side effect of yarn v1 needing all three workspaces' `package.json`s present, not something worth working around (a leaner prod-only install risks yarn's `--frozen-lockfile` check disagreeing with a lockfile computed across all three workspaces). What the file split *does* avoid is the far more expensive part — `Dockerfile.api` never runs `nuxt build`, and `Dockerfile.ui` never runs `nest build`/`prisma generate`.

**`.env`/secrets locations**: `apps/petty-cash-api/.env` + `apps/petty-cash-api/secrets/jwtRS256.key.pub`, and separately `apps/petty-cash-ui/.env` — not repo-root, matching where `env.ts`/`nuxt.config.ts`/`AUTH.md` actually expect them locally. Each `cloudbuild-stag*.yml`'s `SetupEnv` step materializes its own app's files at those paths before `docker build` runs. `cloudbuild-stag-api.yml` also fetches `authjs-public-key` — the existing org-wide shared secret, same key `payouts-api`/`pcs-api` use — never `authjs-private-key`, since `@pension/midgard` only ever verifies tokens, never signs them (`AUTH.md`: "never copy the matching private key; consumer apps don't need it"). `cloudbuild-stag-ui.yml` needs no JWT key at all — `@pension/midgard-nuxt` never verifies tokens locally either.

**`petty-cash-api`'s `.env` is composed from two secrets**, same order as payouts-api's own pipeline: the existing, org-wide shared `stag-nest-api-global` secret (common vars every staging NestJS API needs — `AUTH_ENDPOINT`, `JWT_PUB`, `JWT_LOGGING`, `GRANT_TYPE`, `REDIS_HOST`/`PORT`/`DB`/`PASSWORD`/`PREFIX`) fetched first (`>`), then the new app-specific `petty-cash-api-stag-secrets` secret appended on top (`>>`) so app-specific values (`DATABASE_URL`, `CLIENT_ID`/`CLIENT_SECRET`, `PORT`, `SHORT_DOMAIN`, `APP_NAME`, `APP_ENV`, `REDIRECT_URL`) can still override it. **This wasn't the original design here** — the first version of `cloudbuild-stag-api.yml` only fetched one new secret and told the user to duplicate *every* required var into it, which is how the deployed service actually crashed at startup: `@pension/midgard`'s own `znv`-based env parsing (`AUTH.md`: "it parses the file itself... regardless of whether your own app-level config references them") threw `Errors found while parsing environment: [AUTH_ENDPOINT]: This field is required... [JWT_PUB]: This field is required` — both of those are exactly the kind of common var meant to live in `stag-nest-api-global`, never populated because the pipeline never fetched that secret at all. Caught only after a real deploy actually ran and crashed, not from reading payouts-api's file carefully enough the first time. `petty-cash-ui` doesn't need this two-secret composition — `payouts-ui`'s own pipeline only ever fetches one app-specific secret too, since `@pension/midgard-nuxt` reads config through Nuxt's `runtimeConfig` rather than a strict startup-time schema that throws on missing fields — `petty-cash-ui-stag-secrets` alone is enough.

The two new secrets, `petty-cash-api-stag-secrets` and `petty-cash-ui-stag-secrets`, **don't exist yet** — nothing here provisions them; they have to be created and populated by hand before the first real deploy of each.

**Why `cloudbuild-stag-ui.yml` has no `--vpc-connector`/`--set-cloudsql-instances`**: `petty-cash-ui` only ever calls `petty-cash-api`'s public HTTP API and bifrost's public URL — it has no reason to reach a private-VPC resource (Redis, Cloud SQL) directly. `payouts-ui`'s own `cloudbuild-stag.yaml` sets both flags anyway despite being the same kind of pure-frontend app — that looks like unexamined copy-paste from a backend template, not something to imitate here.

**Neither file passes `--use-http2` (anymore)** — the first version of both did, copied from `payouts-api`'s Deploy step without checking why it was there. `payouts-api`'s own `_SERVICE_NAME` is literally `payouts-grpc` — that flag exists specifically for its gRPC service, which genuinely needs Cloud Run's proxy to speak HTTP/2 to the container. `payouts-ui`'s own cloudbuild file doesn't have it at all. Symptom on the deployed `petty-cash-ui` service: visiting the URL returned `upstream connect error or disconnect/reset before headers. reset reason: protocol error` — a classic Cloud Run/Envoy error meaning the proxy tried an HTTP/2 (h2c) handshake against a container that only speaks HTTP/1.1. Nitro's Node server (what `petty-cash-ui` runs) and NestJS/Express (`petty-cash-api`, via `@nestjs/platform-express`) both default to plain HTTP/1.1 — neither is a gRPC service, so neither needs or should have this flag.

**Just removing `--use-http2` from the Deploy step wasn't enough** — `gcloud run deploy` patches the existing service rather than fully replacing its spec, so a setting from an earlier revision (like the container port's `h2c` name, set by that first `--use-http2` deploy) persists across later deploys that simply omit the flag; confirmed directly via `gcloud run services describe` on both services (`spec.template.spec.containers[0].ports[0].name: h2c` on both, well after `--use-http2` had already been removed from both files). The actual fix is `--no-use-http2` (an explicit disable, per `gcloud run deploy --help`), not the flag's absence — added to both `cloudbuild-stag-api.yml` and `cloudbuild-stag-ui.yml`, next to their `--port` line.

**Real, unrelated finding while diagnosing this**: `gcloud builds describe <id>` returns the exact args used for every step **in plaintext**, including `$_GH_PAT` — Cloud Build substitution values aren't secret just because they're set at the trigger level; anyone with read access to Cloud Build history in this project can read the real GitHub PAT this way. This was noticed by accident while checking a build's Deploy step args, not something being newly introduced — the trigger substitution mechanism (`_GH_PAT: build-arg-gh_pat` as the file default, overridden per-trigger) was already set up this way before this session touched it. Worth moving to Cloud Build's proper `availableSecrets`/`secretEnv` (Secret Manager-backed) mechanism instead of a plain trigger substitution, and rotating the current token since it's now been exposed in build history. Not fixed here — flagging it, not silently changing how secrets are wired without the org's sign-off.

**Verified so far**: `petty-cash-api`'s pipeline now builds, pushes, and *attempts* to deploy successfully end to end (confirmed via `gcloud builds log` against a real build, not local testing) — every bug listed above is genuinely fixed. **Still open, and it's a database issue, not a pipeline one**: the deployed container crashes on startup —
```
PrismaClientInitializationError: Error querying the database: Unknown authentication plugin `mysql_clear_password'.
```
— confirmed via `gcloud logging read` against the crashed Cloud Run revision. Prisma's query engine only speaks `mysql_native_password`/`caching_sha2_password`; `mysql_clear_password` shows up when the MySQL server offers a plugin during negotiation that Prisma can't handle — typically a mismatch between `DATABASE_URL`'s connection method (TCP vs the `/cloudsql/<connection_name>` Unix socket `--set-cloudsql-instances` provisions) and/or the DB user's configured auth plugin, and/or a missing SSL param. This needs someone with access to the actual Cloud SQL instance and the `petty-cash-api-stag-secrets` secret's `DATABASE_URL` value to fix — not something fixable from the Dockerfile/cloudbuild yaml side. `petty-cash-ui`'s pipeline is still being worked through as of this writing (was failing on the shared-stage issue documented above; not yet confirmed clean end to end after that fix).

**Real bugs found via actual Cloud Build runs** (not caught by the local placeholder-token test above, since that never got past the registry-auth step):
- `SetupEnv`'s `gcloud secrets versions access latest --secret=X --format='get(payload.data)' | base64 -d > file` failed with `base64: invalid input`. The simpler `gcloud secrets versions access latest --secret=X > file` (no `--format`/decode at all) works reliably regardless of how the secret was originally uploaded — switched both `cloudbuild-stag-api.yml` and `cloudbuild-stag-ui.yml` to that form. (payouts-api's own pipeline is inconsistent about this — one of its secrets uses the `--format`/`base64 -d` dance, another just redirects the plain output straight into `.env` — so this wasn't a petty-cash-specific mistake to begin with, just an unlucky choice between two patterns that coexist in the reference.)
- `yarn install --frozen-lockfile` failed in the `deps` stage with `error geoip-lite@2.0.3: The engine "node" is incompatible with this module. Expected version ">=24.0.0". Got "22.12.0"` — `geoip-lite@2.0.3` (see the GeoIP section above) genuinely requires Node ≥24, but the `Dockerfile` was on `node:22-alpine3.19` (matching payouts-api's own base image choice, which doesn't hit this since it doesn't depend on `geoip-lite`). **This reproduces locally too** — directly verified with `nvm exec 22 yarn install --frozen-lockfile`, same fatal error, exit code 1, even though `node_modules/geoip-lite` was already sitting on disk from some earlier successful install. No local `.yarnrc`/`.npmrc`/shell env var suppresses the engine check (checked `~/.zshrc`, `~/.yarnrc`, `~/.npmrc`, `env`, and confirmed no Node 24 binary exists anywhere on the machine, inside or outside nvm) — so exactly how that earlier install ever succeeded is genuinely unresolved, not just unexplained-but-assumed-fine; don't trust the local `node_modules/geoip-lite` as evidence this works on Node <24, since a fresh install right now demonstrably does not. Fixed by bumping every `FROM node:...` line in the `Dockerfile` to `node:24-alpine` (there's no `node:24-alpine3.19` tag — confirmed via `docker manifest inspect` — so this also drops the pinned Alpine minor version, unlike the `node:22-alpine3.19` it replaced). Root `package.json`'s own `"engines": {"node": ">=22"}` still trivially allows 24, so this doesn't contradict it — just left as `>=22` rather than bumped to match, since that field is unrelated to this specific Docker build failure.
- `yarn workspace @petty-cash/qr-render build` failed in `api-builder`/`ui-builder` with `error Error: Failed to replace env in config: ${GH_PAT}` — the repo's own committed root `.npmrc` literally contains `_authToken=${GH_PAT}` (a template meant for a real local shell env var yarn substitutes when parsing `.npmrc` — that's how local dev actually authenticates). `COPY . /home/node/` in those stages copies the whole repo, which overwrites the `deps` stage's correctly-generated `.npmrc` (a real literal token baked in via Docker's `ARG GH_PAT` at `echo` time) with that unresolved template — Docker `ARG`s aren't automatically exposed as shell env vars in later `RUN` steps, so yarn's own config-parsing then fails on the literal, un-substituted `${GH_PAT}` the next time *any* yarn command runs in that stage, regardless of whether that command even needs registry access. Fixed by adding `.npmrc` to `.dockerignore` — `COPY . .` never sees it, so the `deps` stage's working one survives untouched into every later stage.
- `petty-cash-api`'s `.env` only had the app-specific `petty-cash-api-stag-secrets` secret in it — never `stag-nest-api-global` (the shared secret with `AUTH_ENDPOINT`/`JWT_PUB`/etc.). This one wasn't caught by a build failure at all — the image built and deployed successfully, then the container **crashed at startup**: `@pension/midgard`'s own `znv`-based env parsing threw `Errors found while parsing environment: [AUTH_ENDPOINT]: This field is required... [JWT_PUB]: This field is required`, since it parses `.env` itself regardless of what the app's own `env.ts` schema references (see `AUTH.md`). Fixed by fetching `stag-nest-api-global` first (`>`) then `petty-cash-api-stag-secrets` appended on top (`>>`), matching payouts-api's exact two-secret composition — see below for the full explanation. `petty-cash-ui` doesn't need this (single secret is enough, same as `payouts-ui`).
- **`COPY failed: stat home/node/apps/petty-cash-api/.env: file does not exist` in the `api-runner` stage, seen from BOTH pipelines** — the biggest bug found in this whole deploy effort, and the reason `Dockerfile.api`/`Dockerfile.ui` are two files instead of one with `--target`. First guessed to be `--cache-from` reusing a stale layer (removed it from both `cloudbuild-stag-api.yml`/`cloudbuild-stag-ui.yml` — a reasonable determinism improvement on its own, but **it wasn't the real cause**, confirmed wrong once the same failure kept happening with `--cache-from` already gone). The real cause, found by actually reading a full `petty-cash-ui` build log end to end (`gcloud builds log <id>`) instead of guessing further from tails: this Cloud Build environment doesn't prune un-targeted stages the way BuildKit does, so a `--target=ui-runner` build was *also* building `api-development`, `ui-development`, and `api-runner` — stages with zero relationship to the UI, `api-runner` among them needing `apps/petty-cash-api/.env`, a file only `cloudbuild-stag-api.yml`'s own `SetupEnv` ever creates. (The single-Dockerfile API pipeline "worked" by comparison only because `api-runner` happened to sit before `ui-runner` in the file, so it never had to build into the UI's territory.) A same-file placeholder-files workaround was tried first and did fix the crash, but left both pipelines still silently building both apps' full builder stages on every push — splitting into `Dockerfile.api`/`Dockerfile.ui` (see the section intro above) replaced that workaround entirely and fixed the actual waste too, not just the symptom. There are no more `api-development`/`ui-development`-style unused stages in either file — each file only contains stages its own pipeline actually needs, so there's nothing left for the classic builder's non-pruning behavior to accidentally build.

Terraform state backend: `iac/staging/backend.hcl` (`bucket = "mpao-stag-tf-states"`, `prefix = "petty-cash"`) — matches `payouts-api/iac/staging/backend.hcl` exactly except the prefix (its own is `"payouts-api"`; an earlier version of this doc claimed neither repo commits a `backend.hcl` at all, found by an incomplete `find` that only checked `backend*.conf` — wrong, payouts-api does commit one, this just copies that same pattern). Run from `iac/staging`:
```bash
terraform init -backend-config=backend.hcl
terraform plan
terraform apply
```
This creates **two** triggers (`petty-cash-api-push-trigger`, `petty-cash-ui-push-trigger`) off one shared `cloudbuild_repo` connection — the `cloudbuild_trigger` module has no path-filter support, so every push to `staging` fires both regardless of which app actually changed; each trigger just points at a different `cloudbuild-stag*.yml`, and each of those now builds from its own `Dockerfile.api`/`Dockerfile.ui`.

Everything in both `cloudbuild-stag*.yml` files' `substitutions` blocks under the "verify before first run" comment (`_CLOUD_SQL`, `_SERVICE_ACCOUNT`, `_VPC_CONNECTOR`, `_DEPLOY_REGION`, `_TRIGGER_ID`/`_LABELS`) was carried over from `payouts-api`/`payouts-ui`'s values on the assumption petty-cash deploys into the same shared staging project (`staging-278118`) — confirmed by the user for the project itself, but specifics like the exact Cloud SQL instance petty-cash's already-set-up staging DB actually uses were never independently confirmed. Note `payouts-api` and `payouts-ui` don't even agree with each other on Cloud SQL instance or deploy region (`asia-east1` vs `asia-northeast1`) — this org's staging apps aren't fully consistent on these, so don't assume petty-cash-ui's chosen region (matched to payouts-ui, the closer same-kind reference) is definitely right either. `_TRIGGER_ID`/`_LABELS` in both files are real placeholders (`REPLACE_WITH_TRIGGER_ID`) — fill them in from `terraform output trigger_id_api`/`trigger_id_ui` after the first `apply`, same as payouts-api's own trigger ID is hardcoded into its `cloudbuild-stag.yml` post-creation.

## Verification

Don't run a full build (`nest build`, `nuxt build`) as your default way to check a change — it's slow and not what's actually being asked for most of the time. **Lint is the standard verification step** for both `petty-cash-api` and `petty-cash-ui`:

```bash
yarn lint            # apps + packages, from the petty-cash root
yarn workspace petty-cash-api lint
yarn workspace petty-cash-ui lint
yarn workspace @petty-cash/qr-render lint
```

Only reach for a full build when you specifically need to catch something lint can't — e.g. verifying a production bundle, or a type error lint doesn't cover.

For anything touching the Prisma schema or the domain endpoints, lint alone isn't enough — actually run it:

```bash
yarn workspace petty-cash-api db:migrate   # applies schema.prisma changes to the local `petty-cash` MySQL db
yarn workspace petty-cash-api db:seed      # seeds one demo ShortLink (shortCode "demo") + its QRCode, for exercising the redirect engine
```

Then boot (`yarn dev:api`) and curl: guarded routes should `403` unauthenticated; `GET /demo` (or whatever code you seeded) should `302` and actually increment `clicks`/write an `EngagementEvent` — check the DB directly (table/column names are snake_case, e.g. `docker exec mysql-default mysql -uroot -proot petty-cash -e "SELECT short_code, clicks FROM short_link;"`) rather than trusting the HTTP response alone, since a bug could still return the right status code while silently failing to persist.

A real authenticated round-trip (browser login through `petty-cash-ui` → real bearer token → `200` from a guarded CRUD route with real data) has been verified — see `AUTH.md`'s "REDIS_DB must match bifrost's, and REDIS_PREFIX must be empty" gotcha for the fix that made this work at all; it was broken for the entire domain-backend build and only fixed afterward. `petty-cash-api`'s own `client_credentials` (`CLIENT_ID=hcs-client-4321`) is a separate, still-unverified thing — it's for `petty-cash-api` acting as a client calling some *other* service, which nothing in this app currently needs; don't confuse it with the (working) user-login path above.

`prisma migrate reset`/`migrate dev` against the local dev DB is a real destructive action (drops all tables) — Prisma itself now hard-blocks an AI agent from running it without the user explicitly consenting in-conversation first (`PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION`). Don't try to route around that block; ask.
