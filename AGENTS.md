# MPAO Petty Cash

Petty Cash manages petty cash between MPAO General Services (GS / Procurement) and Finance. It is not a URL shortener. The applications are `apps/petty-cash-ui` (Nuxt 3 SPA / Pinia) and `apps/petty-cash-api` (NestJS 10 / Prisma / MySQL). They communicate directly using authenticated HTTP. No gateway or Nuxt API proxy. Business endpoints are unversioned and have no application prefix: `/requests`, `/fund`, `/vault-counts`, `/files`, etc.

The product name is **Petty Cash**. Use it in all user-facing copy, error messages, page titles, reports and documentation. Internal codenames and existing identifiers are implementation details, never product branding. The API machine identifier is the lowercase slug `APP_NAME=petty-cash`; never use the display name as the permission prefix.

## Access — mandatory on every business endpoint

Read `AUTH.md` for Bifrost/Midgard setup. Bifrost `/me` is the only identity source; use the existing Midgard integration. Do not add a local `/me` endpoint, identity service or users table. `/access` returns application roles, capabilities and the caller’s active requester/approver staff eligibility; it never serves as an identity endpoint.

Every business controller uses `@UseGuards(IdentityGuard, EntityGuard, PermissionGuard)`. `GET /access` and `POST /idempotency-keys` are explicit exceptions: use only `IdentityGuard` and `EntityGuard`, with no separate action permissions. Access reports the caller’s capabilities (all false when none are granted); retry keys grant no business authority. Expenses uses a narrow PermissionGuard subclass that also accepts `expenses.addexpense` for removal, as explicitly requested; standard identity/entity checks and all other permission checks remain unchanged. `EntityGuard` follows the reference in `verification-api/src/auth/entity.guard.ts`: the verified Bifrost user's active numeric `transacting_as` must equal configured `MPAO_ENTITY_ID`. Membership alone is insufficient. Missing/invalid configuration fails API startup and the guard fails closed. Configure the verified Bifrost MPAO entity ID, not an organisation name or UUID.

Permissions follow Midgard's standard `{APP_NAME}.{Controller}.{handler}` convention, with `Controller` removed from the class name and the complete permission key lowercased. Keep TypeScript class and handler naming conventions unchanged; Midgard checks permissions case-insensitively. PermissionGuard discovers these through `/midgard/permissions/sync`; Bifrost also uses its library-provided `/api/v1/midgard/permissions/sync` alias. `APP_NAME=petty-cash`. Use the contribution-api/contribution-ui permission pattern. As explicitly requested, `APP_ENV=development` bypasses permissions; production enforces them. Identity and EntityGuard remain mandatory in development.

Every handler resolves `@CurrentActor()` through ActorPipe, which calls the installed IdentityService.hasPermission evaluator for the known controller/actions. Services and UI capabilities check these individual action permissions, never synthetic role-permission keys. The actor's GS/Finance labels are derived only for notification audiences and display/audit. Bifrost roles group permissions; the application does not own role assignments. Ownership, workflow state, revision checks and financial invariants remain enforced in every environment. Keep the root `permissions.json`, `auth/permissions.ts`, Midgard discovery and `docs/sql/petty-cash-permissions.sql` synchronized whenever permissions change. See `docs/PERMISSIONS.md`.

Sidebar visibility and direct page entry follow server `view*` capabilities. Use dedicated `approvals.list`, `disbursements.list` and `requests.history` view permissions for GS Approvals, Finance Desk and History. `requests.list` controls Requests, `vaultcounts.list` Reconciliation, and `fund.transactions` Ledger. Action permissions never implicitly reveal a page. Provision **Petty Cash Request Role** and **Petty Cash Finance Role** using the templates in `auth/permissions.ts` and the matching SQL; Bifrost owns assignments. Do not grant the Request role Finance view permissions merely to satisfy unnecessary frontend fetches.

## API feature structure

Follow the reference project's feature folders: each feature owns its module, controller, service and `dto/` files for its inputs. Features are requests, approvals, disbursements, expenses, settlements, fund, vault-counts, files, notifications, statistics, reports, access and OCR. Register them through Nest dependency injection. No central Petty Cash controller/service and no dynamic `:action` route or action switch.

Each transition has an explicit controller route and named feature-service method. Zod schemas and inferred DTOs live with their feature. Shared pagination, validation, dates, decimal arithmetic and serialization belong in `common/`. The shared request workflow coordinator only handles locking, revisions, policy checks and transactional audit/notifications; the calling feature implements the operation. LedgerService owns cash movements. Pass the existing Prisma transaction client through every participating service; never split a financial operation across transactions.

Commands use a separate Nest application context in `src/cli.ts`, with no HTTP controllers or Bifrost connection. Bootstrap belongs to the fund feature; MaintenanceService coordinates file cleanup and notification reminders. See `docs/API_STRUCTURE.md` for routes and dependencies.

## Domain flow

GS Staff creates → GS Manager authorizes → Finance prepares and notifies → GS confirms collection → GS records receipts and settles → Finance finalizes → Finance periodically counts the vault.

Statuses: pending_approval → pending_finance → ready_for_collection → cash_issued → pending_closure → closed. Rejection is terminal. Finance can return pending_closure to returned_for_correction; GS corrects and settles again. Approval and rejection depend on their individual permissions and pending_approval status, including for the requester; self-approval is allowed by explicit user decision. Finalization likewise depends on settlements.finalize permission and pending_closure status, including for the requester. Only the owner edits pending requests. Requested petty cash is capped at MVR 5,000 per request (API `MAX_REQUEST_AMOUNT`, mirrored in the UI). For now `/requests` and `/requests/history` list only the caller's own requests; `GET /requests/:id` is limited to the creator and holders of `approvals.list` or `disbursements.list`. GS Approvals and the Finance Desk list every requester's requests. Receipts can change only in cash_issued / returned_for_correction. Anyone eligible to add receipts can also remove them on that request; pending_closure and closed lock both actions. Removal retains file evidence and audit history. No direct status DTO. `allowedActions` uses the same policy as mutation authorization.

## Cash and audit invariants

One fund: FUND-MVR-01, MVR, business timezone Indian/Maldives. UTC timestamps; date-only fields stay YYYY-MM-DD. Prisma names are camelCase; every database table/column is mapped to snake_case. Table names are plural and have no codename prefix (`funds`, `requests`, `fund_transactions`, `receipt_files`, etc.). Keep raw SQL lock/idempotency queries aligned with schema @@map names. Rename populated tables through an additive migration; never rewrite already-applied migrations or reset data to resolve naming changes. Money is Decimal(14,2), never floating-point backend arithmetic. Decimal `isPositive()` includes +0; use `gt(0)` for strictly positive comparisons.

Vault = opening balance + top-ups − collections + returns − reimbursements ± adjustments. Preparing cash creates no ledger row. GS confirmation creates one acknowledged issuance and a debit. Preparing Finance officer and acknowledging GS recipient are distinct actors. Finalization is one transaction: count actual returned cash and credit it, reimburse overspend, or no ledger movement for exact spend; close and audit together. The GS settlement declaration is retained separately from Finance's counted return. Return discrepancies are retained. Every state change writes audit history; removed expenses retain their evidence.

Only LedgerService writes ordinary cash movements, under a fund-row lock. Bootstrap writes the single opening row. MySQL triggers prohibit ledger UPDATE/DELETE. Annual voucher counters are transactional. Generate all UUIDs in the API, never in frontend code. Financial actions obtain a key from guarded `POST /idempotency-keys` before submitting an Idempotency-Key header; retries reuse that server-issued key and payload. Bulk receipt confirmation also requires a server-issued retry key and saves the entire batch atomically; other nonfinancial saves do not request retry keys. Key acquisition belongs inside the submission try/finally so failures always release the busy state. Every request mutation requires expectedVersion; revisions protect stale edits; they are not API versioning.

Counts snapshot expected cash under the fund lock. Resolve applies the saved difference to the current ledger; it must not overwrite later legitimate transactions. Reject adjusting an older count after a newer count or adjustment. Supervisors can resolve without an adjustment. Counts due after seven days generate a daily deduplicated in-app reminder.

Denominations are defined once in `packages/denominations/definitions.json` for the API, UI counters and PDFs. Keep `minorUnits` authoritative for exact client display totals; `coin0_1` denotes one laari, not ten. An empty count form is not a zero count: require an explicit entry, allowing zero.

## Files — always stream

Browser File multipart → authenticated controller → Busboy → bounded signature/size validation → storage write stream. No base64, Multer memory storage, full-file Buffer accumulation, or production disk staging. Prefix validation buffers at most 64 bytes. Limit one file and 10 MiB while consuming bytes; supported JPEG, PNG, HEIC, WebP, PDF. Use GCS in deployment, private disk only in development.

Never hold a DB transaction across an upload. A file is attachable only after completed storage persistence and ready metadata. Abort/failed/truncated streams remove partial storage; maintenance retries cleanup of abandoned records after 24 hours. Attached files are retained. Downloads stream through MPAO-authenticated endpoints, never public/signed bucket URLs. The UI may create transient blob URLs after authenticated retrieval; never persist those as receipt identifiers. Optional receipt extraction uses server-side GEMINI_API_KEY and streams saved private files to the Google Files API; never inline/base64 or buffer entire receipts. POST /ocr/receipts accepts only an owned ready fileId. Show upload/extraction progress and hide the form and Save button while extraction is running. Open the editable form after completion or failure; preserve manual edits and ignore late results after close/reset/save. Classify bill/receipt/invoice versus other/unknown before prefilling; unrelated or unreadable files show a clear message and manual entry without AI-invented values. Copy exact purchased line-item descriptions, retaining sizes and pack notation; exclude payment/bank/unit-conversion rows. Join purchased item names with commas in What was bought. Validate AI suggestions and never mark them verified. Delete temporary Google files after extraction; provider expiry is the fallback. See docs/RECEIPT_AI.md.

## Frontend conventions

Keep ssr:false and the explicit main layout (auth callbacks must not render the app shell). Use useHttp with uppercase methods; multipart uploads use fileUpload:true and the actual File. The protected preview helper uses native authenticated fetch because Midgard's download helper does not return bytes. Await writes, disable repeats, retain failed form state and show the backend message. Do not turn failed refreshes after a committed financial write into failed payment submissions. Cache list summaries separately from details; PDF downloads fetch complete details/reports. Statistics and totals come from the server, never the visible page. Clear cached state on identity/organisation changes.

The main layout has one immediate route/identity watcher, without a second mounted initialization. Store initialization and in-flight GETs coalesce. Navigation fetches only its page data; statistics/fund reads are reusable for 30 seconds and notifications for 60 seconds. Writes invalidate read caches and refresh current-page data; identity/organisation/permission changes discard caches and reject late responses. Do not increment the identity generation on navigation or load fund, statistics and notifications unconditionally on every menu click.

PoSelectField uses primitive IDs by default; add object only when the model holds an object. Preserve escaping of user content in PDF HTML. UI-kit formatting wrappers normalize nullable output without changing presentation.

## Staff settings

Settings preserves the ui-lab Petty Cash view and uses an Add staff button with work-email lookup, employee review and explicit confirmation. CommonService.FindStaffByEmail is the source for staff details. StaffAssignments owns `staff_assignments`: active requester/approver entries, soft deletion, re-addition as a new dated entry and retained actor/history fields. Lock a permanent `staff_assignment_types` row for every change; reject active duplicates by employee ID/type and removal of the final active person of either type. Initial setup may be empty until real staff are added. Settings view/lookup/add/remove require their own staffassignments permissions. All four are included in the Finance role; the Request role receives none.

Frontend request actions require both existing allowedActions/permissions and active requester assignment; approval/rejection require existing permissions and active approver assignment. Receipt upload/extraction likewise require their individual permissions and requester assignment. Preserve all ownership/state rules and leave backend business authorization permission-based. Match assignments using the verified Bifrost person's entity_id, never the active organisation ID or browser-supplied identity. Recheck frontend eligibility before submission, refresh on navigation/periodically, and clear it on identity changes or access refresh failure.
